# 京东三个独立青龙任务

包含 PLUS 每日盲盒、每日刮卡领豆、京喜自营店签到。三个任务独立启停，与 Faker 订阅分开；没有加入普通签到、种豆或金融。保留原 Loon 脚本和手动入口。

此版迁移现有业务流程，使用 Node 内置模块适配 Loon，沿用已核查的官方 SDK 和活动签名逻辑，不调用第三方签名服务。尚未证明这三个活动可以仅凭 `JD_COOKIE` 自动取得全部设备参数，因此当前仍需要从手机同步活动记录。已通过模拟接口测试，NAS 实际签到结果需首次运行确认。

## 1. 同步自己的凭据

更新 Loon「青龙任务接入」插件：

`https://raw.githubusercontent.com/LazingLuo/LazingLuo_Loon-Rules/refs/heads/main/Plugins/qinglong-bridge.plugin`

原来面板地址、Client ID、Secret 保留。手动操作选「同步活动凭据」，运行「青龙手动操作」。青龙环境变量中应有已启用的 `JD_COOKIE` 和 `LAZING_JD_ACTIVITY_V1`，后者是活动请求、签名环境的 JSON 包，不需要手工填写。已抓取的记录可直接同步；缺失某项时，开启该原插件的获取开关、进入相应页面后再次同步。

需要后续自动同步时，可打开「同时同步独立活动凭据」及「自动同步凭据」。手机须能访问 NAS。同步只更新凭据，不触发签到，也不重新登录京东。


## 3. 首次运行与定时

先逐个手动运行一次，看青龙日志中的结果。完成、今天已领取、盲盒没有机会都会正常结束；状态不明确、凭据错误、网络错误会停止，不自动重试领取。

三个默认时间是每天 00:02、00:07、00:12，全部可在青龙任务编辑界面修改。命令使用普通 `task ...`，继承你现有青龙的随机延迟设置；本脚本不再加一层随机等待。若全局设为 2000 秒，各任务会分别随机等待，再启动 Node 进程，等待期间不占用活动执行锁。

青龙实际运行正常后，请关闭这三项对应的 Loon 自动签到开关，保留 Loon 手动入口。两个系统没有共享执行锁，避免同时运行同一个活动。手机已经提交过的当日记录会随活动包同步，青龙也会保留自己的提交记录，以免迁移后重复领取。

## 结果和通知

每项任务各自保存结果、历史、SDK 缓存和领取提交记录。默认目录 `/ql/data/lazing-jd/`，已挂载的 `/ql/data` 能跨容器重建保留。环境变量 `LAZING_JD_DATA_DIR` 可指定其他持久化目录。文件权限为 600，路径使用账号摘要，不直接显示账号。

日志显示成功或失败及数量、连签天数等已有信息；不会输出 Cookie、设备令牌或签名环境全文。存在青龙常用的 `/ql/data/scripts/sendNotify.js` 或同订阅根目录的 `sendNotify.js` 时使用其通知渠道；没有通知模块时，以任务日志为准，不需要为签到安装额外依赖。

遇到未登录时，在 Loon 更新并同步凭据；签名版本不兼容时按日志处理，不能仅靠更新 Cookie 修复。普通凭据更新不会清除青龙已提交记录。领取请求失败但结果不明确时，当天再次运行只查询，不重复提交。

如果 Node 被强制杀死导致残留 `running.lock`，脚本会停止并提示。确认青龙没有同项任务运行后，只清理该任务目录的 `running.lock`，保留 `state.json` 中的领取记录。

## 维护与验证

`function/jd-core.js`、`function/jxzy-core.js` 分别是当前 Loon 对应源文件的固定快照，此次未更改业务逻辑。以后原 Loon 源文件更新时，需要同步核查青龙快照，不能假设二者自动联动。

离线验证：`node Qinglong/test.cjs`。测试全部使用虚构账号及模拟响应，覆盖三项已领跳过、成功领取、状态复查、网络结果不明确、跨次提交记录、同账号 Cookie 更新、Loon 提交记录导入、并发锁、超时释放、目标域名和敏感信息检查。没有调用京东真实账户接口，也没有在 NAS 上执行领取。
